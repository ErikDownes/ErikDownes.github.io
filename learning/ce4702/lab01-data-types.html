Data types are contracts

Before statistics, algorithms or machine learning, a computer needs an exact representation of the thing you mean. A value is not simply “data”: it has a type, a valid range, a representation and permitted operations.

Learning target: explain why "87" and 87 are different, convert text safely, validate ranges, and recognise that bad representation creates bad analysis before any sophisticated method begins.

Start with a record

Suppose one line from a CSV file is:

1001,12,87

We decide that it means:

  • ID = 1001
  • attendance = 12
  • score = 87
Predict · What type is the CSV line when Java first reads it?

Text. The whole line is initially a String. Splitting it gives more strings. We still have to parse the numeric fields.

Predict · Why not leave attendance as the string "12"?

Because arithmetic and numeric comparisons should operate on a numeric representation. The string is the input representation; int is the representation we want for calculation.

Read the program as a data pipeline

The program performs a tiny version of a real data pipeline:

raw text → split fields → parse types → validate → calculate → report

Explain · Where could the program fail?

Wrong number of fields; text where an integer is expected; values outside the allowed range; assumptions about what each column means. Each failure should be explicit rather than silently producing a misleading answer.

Change · What happens if score becomes 105?

The parser can still convert "105" to an integer, but conversion is not the same as validation. The program should reject it because the score rule is 0–100.

Deeper question · Why is this relevant to data analysis?

A statistical method cannot repair a variable whose meaning, type or valid range was misunderstood. Data quality begins with representation and validation.

My task

  2. Before changing anything, predict the result for 1002,0,40.
  3. Change the record and run it.
  4. Try 1003,twelve,70. Explain the failure.
  5. Add a fourth field called year.
  6. Decide its type and validation rule.
  7. Add one self-check that proves your new rule works.
  8. Commit the change with a message that explains what you learned.

What to be able to say afterwards

“When data comes into a program it often arrives as text. I need to decide what each field means, convert it to an appropriate type, validate it, and only then calculate with it. Parsing tells me whether a conversion is possible; validation tells me whether the value is acceptable.”
